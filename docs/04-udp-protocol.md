# 04 · UDP 协议与状态机

> ⚠️ **上位机对接请直接看 [07-host-integration.md](07-host-integration.md)。**
> 本文是协议的设计稿与原理说明；07 是实现契约（含实际 IP、字段边界、排错表）。
> 两者冲突时以 07 为准。

## 4.1 设计原则

| 原则 | 说明 |
|---|---|
| **单向** | 模块永远不往上位机发业务数据（只有可选的 Serial 日志和未来的心跳）。没有握手、没有重传、没有 ACK |
| **无连接** | 上位机随时可以起停，模块不感知、不需要重连流程 |
| **latest-wins** | 灯阵只关心"此刻该显示什么"。旧帧毫无价值，**收到就覆盖单缓冲，不排队** |
| **丢包不补** | UDP 丢一帧，下一帧马上会来。补帧带来的延迟远比丢一帧难看 |

> **为什么不能用队列：** 如果上位机以 200 fps 发而灯阵只能吃 129 fps，队列会让延迟线性累积，几秒后显示的内容就滞后现实好几百毫秒。latest-wins 则**端到端延迟恒定**（约 7.7 ms），丢掉中间帧只是"跳过"，肉眼几乎看不出来。

## 4.2 传输参数

| 项 | 值 |
|---|---|
| 传输层 | UDP |
| 模块监听端口 | **8551**（可在固件改） |
| 目标 | 建议给模块配置**静态 IP**，上位机单播该地址 |
| 广播 | 不推荐（会唤醒网段内所有设备，且丢包率更高） |
| MTU | 最大包 776 B < 1472 B，**不触发 IP 分片** |

> 用静态 IP 的理由：ESP8266 的 DHCP 重连可能耗时数百毫秒到数秒，掉电再上电时会拉长冷启动到第一帧的时间。静态 IP 直接跳过这段。

## 4.3 包格式（通用包头 8 字节）

```
 0      1      2      3      4      5      6      7      8 ...
┌──────┬──────┬──────┬──────┬─────────────┬──────┬──────┬─────────────
│ 0x4D │ 0x50 │ ver  │ type │  seq (LE)   │ brt  │ rsv  │  payload ...
│ 'M'  │ 'P'  │ =1   │ 1/2/3│  uint16     │ uint8│ =0   │
└──────┴──────┴──────┴──────┴─────────────┴──────┴──────┴─────────────
```

| 字段 | 偏移 | 类型 | 说明 |
|---|---|---|---|
| magic | 0–1 | `'M' 'P'` (0x4D 0x50) | 丢弃所有非此开头的包，防止网段里的其它 UDP 流量污染画面 |
| version | 2 | uint8 | 当前 **1** |
| type | 3 | uint8 | 1 = 表头值 / 2 = 像素帧 / 3 = 授时 |
| seq | 4–5 | uint16 **小端** | 每类包独立递增，用于丢包统计，**不做重传** |
| brightness | 6 | uint8 | 全局亮度 0–255，仅 type=2 生效；**固件侧硬上限 128**，写 255 会被压到 128 |
| reserved | 7 | uint8 | 置 0，保留 |
| payload | 8– | 见下表 | |

**字节序：所有多字节字段一律小端（little-endian）**，与 ESP8266/X86 一致，上位机在 Java/C# 里注意显式转换。

## 4.4 三类载荷

### type = 1 · 表头值（总长 18 B）

```
payload: 5 × uint16 LE，依次为通道 1..5
值的含义：0 = 零位，65535 = 满偏，线性映射（用户确认不做非线性曲线）
```

| 建议发送频率 | **10 Hz**（用户定） |
|---|---|
| 超时 | **5 s** 未收到 → 表头进入演示模式（5 路相位错开的三角波扫针，缓动过渡，不瞬跳） |

### type = 2 · 像素帧（总长 776 B）

```
payload: 768 字节 = 256 像素 × 3 字节 RGB
顺序：行优先 row-major，i = y * 32 + x，x 先变
      payload[3i]=R, payload[3i+1]=G, payload[3i+2]=B
原点：左上角 (0,0)，y 向下增大
⚠️ 这是逻辑 XY 顺序，不是硬件串号顺序 —— 硬件重映射由固件完成
```

| 建议发送频率 | **60 fps** |
|---|---|
| 超时 | **5 s** 未收到 → 灯阵切彩虹时钟 |
| 线上传输时间 | 7.68 ms + 50 µs 锁存 = 7.73 ms |

### type = 3 · 授时（总长 12 B，可选）

```
payload: uint32 LE，Unix 时间戳（UTC 秒）
```

- 主时间源是模块自己的 **NTP**，此包**仅作偏差校正**。
- 固件收到后：`if (|host_unix - local_unix| > 5) local = host_unix;`
- 只在校准偏差超过 **5 秒**时才纠正，避免与 NTP 反复抢时间造成指针/秒跳。
- 必须做合理性判断：`< 1700000000`（2023-11 之后）的包一律丢弃。
- 建议上位机每 10 s 发一次，或完全不发（NTP 够用）。

## 4.5 状态机

```
                    ┌─────────────┐
      上电 ────────▶│    BOOT     │  表头扫针自检 0→满→0
                    │             │  同时后台连 WiFi + NTP
                    └──────┬──────┘
              时间有效？    │
         ┌─────────────────┴─────────────────┐
         │ 否                              │ 是
         ▼                                 ▼
   ┌───────────┐                    ┌─────────────┐
   │  WAITING  │◀──── 时间失效 ─────│    CLOCK    │  彩虹 HH:MM
   │ 滚动文字  │───── 时间就绪 ────▶│             │
   └─────┬─────┘                    └──────┬──────┘
         │                                 │
         └──────────── 收到 pixels ────────┘
                            │
                            ▼
                     ┌─────────────┐
                     │    LIVE     │  渲染上位机画面 + 上位机表头值
                     └──────┬──────┘
                            │
              pixels 超时 5s┘
                            ▼
                    回到 CLOCK / WAITING
```

| 状态 | 灯阵显示 | 表头 | 进入条件 |
|---|---|---|---|
| **BOOT** | 全灭 | 扫针自检（约 1.2 s） | 上电复位 |
| **LIVE** | 上位机像素帧 | 上位机值（带缓动） | 收到 type=2 包 |
| **CLOCK** | 彩虹 HH:MM:SS（+ 底行秒进度） | 演示扫针 | type=2 超时 5 s **且**时间已同步 |
| **WAITING** | "WAITING" 滚动 | 演示扫针 | type=2 超时 5 s **且**时间未同步 |

**优先级：LIVE > CLOCK > WAITING。**

> 为什么要保留 WAITING：时钟恰恰是在上位机失联时才显示的，但**冷启动 + NTP 尚未同步**（路由器断电恢复、WiFi 重连中）时模块手上没有可信时间。这时不能显示 `--:--`，也不能显示 1970，只能滚动文字告诉用户"我在等人"。

## 4.6 表头与灯阵的两条超时独立计价

| 通道 | 超时 | 超时行为 |
|---|---|---|
| 表头 | 5 s（自最后一个 type=1 包起算） | 进入**演示模式**：5 路相位错开的三角波扫针，缓动过渡（不瞬跳） |
| 灯阵 | 5 s（自最后一个 type=2 包起算） | 切 CLOCK / WAITING |

这意味着可以出现组合态：**灯阵 LIVE 而表头已超时**（上位机还在推画面但停止推表头值），此时灯阵继续显示上位机画面、表头跑演示扫针。这是期望行为。

> 表头演示模式与上电首次演示（`!gMeterLinked`）共用同一段三角波 `demoTriangle()`，5 路相位各错开 1/5 周期。区别仅在日志：前者打印"超时 → 演示模式"，后者无日志。收到任何 type=1 包即恢复 LIVE。

## 4.7 固件侧收包流程

```cpp
void loop() {
    const uint32_t now = millis();      // ★ 整个 loop 只用这一个时基

    // 1) 尽可能多地把 socket 里的包读空（latest-wins 的关键）
    int sz;
    while ((sz = udp.parsePacket()) > 0) {
        if (sz < 8 || sz > 800) { udp.flush(); continue; }   // 长度不合法，丢弃
        udp.read(rxBuf, min(sz, sizeof(rxBuf)));
        handlePacket(rxBuf, sz, now);   // ← 时间戳用传进来的 now，不再自己取
    }

    // 2) 灯阵：只要 DMA 准备好就推一帧（永远显示缓冲里的最新帧）
    if (now - lastPixelPush >= frameIntervalMs && strip.CanShow()) {
        if (state == LIVE) {
            applyGammaAndPowerCap(pixelBuf);   // 见 05
            strip.Show();
        }
        lastPixelPush = now;
    }

    // 3) 表头：100 Hz 缓动渲染
    if (now - lastMeterTick >= 10) { updateMeters(); lastMeterTick = now; }

    // 4) 超时检测
    checkTimeouts(now);
}
```

**要点：**
- `parsePacket()` 循环必须**读到空为止**。若每 loop 只读一个包，而上位机发得比 loop 快，socket 缓冲会堆积，导致延迟线性增长 —— 这就是"队列化"的隐形版本。
- `CanShow()` 是 DMA 是否空闲的判据，**一定要查**，否则 `Show()` 会阻塞等待。
- ★ **`millis()` 每个 loop 只调一次**，把 `now` 往下传。这一条看着像是风格问题，实际是个能咬人的正确性约束 —— 原因见 4.9。

## 4.8 上位机侧的强制要求

1. **即使画面内容没有变化，也必须持续按 60 fps（或至少 1 Hz 保活）发包。**
   常驻上位机程序很容易做"内容没变就跳过发送"的优化 —— 那会让模块在 5 秒后判定掉线，每隔 5 秒闪一次时钟，这是最容易踩的坑。
2. 优先推 raw 比特，别在发送前做帧压缩/差分 —— 776 B 的裸数据 @60 fps 只有 47 KB/s，压缩带来的收益远小于复杂度。
3. 退出程序时不需要发"结束信号"，模块 5 秒后自己会切时钟。

## 4.9 参考发送端（Python）

```python
import socket, struct

HOST = ("192.168.1.50", 8551)          # 模块静态 IP
sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)

seq = 0
def send_pixels(frame_rgb: bytes, brightness: int = 60):
    """frame_rgb: 768 字节，行优先 RGB"""
    global seq
    hdr = struct.pack("<BBBBHBB", 0x4D, 0x50, 1, 2, seq & 0xFFFF, brightness, 0)
    sock.sendto(hdr + frame_rgb, HOST)
    seq += 1

def send_meters(values5):
    """values5: 5 个 0..65535"""
    global seq
    hdr = struct.pack("<BBBBHBB", 0x4D, 0x50, 1, 1, seq & 0xFFFF, 0, 0)
    sock.sendto(hdr + struct.pack("<5H", *values5), HOST)
    seq += 1
```

## 4.10 可观测性

固件通过 `Serial`（GPIO1 / TX，115200，USB 直连可见）周期性输出一行诊断：

```
[LIVE] fps=60.0  pkt=18234  loss=0.3%  brt=60  clkV=48  mA=410  cap=0  bad=0  secrow=进度条  rssi=-48  heap=28320
```

| 字段 | 含义 |
|---|---|
| state | 当前状态机状态（方括号内） |
| fps | 实测推帧帧率 |
| loss | 由 seq 断号统计的丢包率 |
| mA | 当前帧软件估算电流（见 [05](05-power-budget.md)） |
| cap | 本周期内触发软件功耗封顶的帧数（>0 表示画面被整体压暗） |
| bad | magic / 版本 / 长度 / type 非法的包数（**>0 一定是上位机的包格式写错了**） |
| rssi | WiFi 信号强度，<-75 就该排查天线/位置 |
| heap | 剩余堆内存，长期运行应基本恒定 |

> 实际格式以此处为准，对接期的字段解释与排错表见 [07 §7](07-host-integration.md)。

> **关于日志串口（阶段 0/1 实测结论）：**
> - `Serial` **可以用来输出**——它的 TX 是 GPIO1，不受影响，USB 上直接能看到日志。本项目的诊断输出就走 `Serial`。
> - `Serial` **不能收命令**——RX 是 GPIO3，已被 DMA 占用。想做串口交互必须改用按键。
> - 若哪天需要把 GPIO1 腾出来，可改用 `Serial1`（TX only，GPIO2）输出，接一个 USB-TTL 即可。

## 4.11 已修复：推流时画面闪回时钟（2026-09-26）

### 现象

上位机正常按 60 fps 推像素帧，灯阵却**偶发闪一下彩虹时钟**，毫无规律，有时几秒一次。

### 根因：一次 loop 里用了两个时刻的 `millis()`

```cpp
void loop() {
  const uint32_t now = millis();      // ← 时基 A
  pumpUdp();                          // ← 内部 handlePacket 又调了一次 millis()（时基 B）
  ...
  withinTimeout(gLastPixelPacketMs, now, kPixelTimeoutMs);   // ← 用 A 去比 B
}
```

`handlePacket()` 里是 `gLastPixelPacketMs = millis();`，而这个函数在 `pumpUdp()` 期间执行，**晚于** loop 开头取到的 `now`。只要这中间的 `millis()` 跨过一个毫秒，`lastMs` 就 > `now`，于是：

```cpp
now - lastMs        // 无符号下溢 → 接近 2^32 的巨大值
   < 5000 ?         // 当然不成立 → 判定超时
```

于是每次收到包都会让紧随其后的**那一次判定**误判超时 → 画一帧时钟 → 下一个包到达又回到 LIVE。**这就是成对出现的 `[State] -> CLOCK / -> LIVE`**。

判据：`[State]` 行**成对着出现、间隔只有几十毫秒** —— 而超时阈值是 5 s。两者差三个数量级，一眼就能排除"真的超时了"。

### 修复

把 `now` 作为参数贯穿：`loop() → pumpUdp(now) → handlePacket(p, len, now)`，
包内的所有时间戳（`gLastPixelPacketMs` / `gLastMeterPacketMs` / `gLedOffAtMs`）统一用它，**不得再调用 `millis()`**。

同时给 `withinTimeout()` 加了一道兜底：`lastMs` 落在 `now` 之后时按未超时处理，避免同类错误再次表现为闪烁。

### 验证方法（可复用）

三段式探测：用同一个脚本一边推 UDP、一边读串口，一次就能分清是固件侧还是发送侧的问题：

| 阶段 | 动作 | 期望 |
|---|---|---|
| 0 | 静置、不推包 14 s | 有第三方在推的话这里就会显示 LIVE ← 这一步能排除干扰源 |
| 1 | 按 60 fps 推 30 s | **全程 `[State]` 行数为 0** |
| 2 | 停推后静置 12 s | 恰好约 5 s 后出现一次 `-> CLOCK` |

修复前阶段 1 会刷出大量成对 `[State]`；修复后全程只有 2 次正常切换（`-> LIVE` 和 `-> CLOCK`）。

> 这个 bug 只在「接收方处理快于毫秒级」时才偶发，静态阅读代码极难发现。
> **通用教训：任何用超时判定驱动状态机的循环里，一轮只能取一次时间基准。**
