# 03 · 32×8 像素索引映射（最容易出错的一环）

> **这一页是整个项目出错概率最高的地方。** 错在这里不会烧任何东西，但会让后续所有调试变成在墙上找门 —— 你会以为是 UDP 解析错、以为是分包丢帧、以为是时序问题，其实是坐标写错了。

---

## 3.1 几何定义

```
物理：4 块 8×8 WS2812B 横排 → 逻辑屏幕 32（宽）× 8（高）
数据：4 块串成一串，共 256 颗，串号 0..255 沿 DIN 方向递增
坐标原点：(0,0) 在**屏幕左上角**，x 向右增大（0..31），y 向下增大（0..7）
```

## 3.2 两块事实（来自已跑通硬件的参考工程）

参考工程：作者本地另一个 ESP32-SOLO-1 + ESP-IDF 工程（同为 32×8 / 256 颗，未包含在本仓库）

**`config.h`：**
```cpp
constexpr bool TILE_ROW_SERPENTINE = false;   // ← 不是蛇形
constexpr bool TILE_ROTATE_LEFT_90 = true;    // ← 每块相对屏幕左旋 90° 安装
```

**`effects.cpp` 的 `xyToIndex()`：**
```cpp
const uint8_t tile     = x / 8;          // 第几块（0..3）
const uint8_t logicalX = x % 8;          // 块内列（0..7）
const uint8_t mappedX  = (8 - 1) - y;    // 旋转后：块内 X ← 屏幕 Y 反向
const uint8_t mappedY  = x % 8;          // 旋转后：块内 Y ← 屏幕 块内 X
return tile * 64 + mappedY * 8 + mappedX;
```

### 合并后的唯一公式

```
index(x, y) = (x / 8) * 64  +  (x % 8) * 8  +  (7 - y)
              └─ 第几块 ─┘    └─ 块内行 ─┘    └ 块内列 ┘
```

### C 实现

```cpp
constexpr uint16_t xyToIndex(uint8_t x, uint8_t y) {
    return ((uint16_t)(x / 8)) * 64 + ((uint16_t)(x % 8)) * 8 + (7 - y);
}
```

> ⚠️ **不要自己重新推导。直接用上面这个公式。** 它不是从"最优雅的做法"来的，它是从你们已经点亮过的那块板子的真实物理走线反出来的。改任何一项都要重新拿到硬件上验证。

## 3.3 关键坐标对照表（照这个逐项核验）

| 串号 | 屏幕坐标 (x, y) | 物理位置 |
|---|---|---|
| **0** | (0, 7) | 第 0 块起点 = **屏幕左下角** |
| **7** | (0, 0) | **屏幕左上角** |
| 8 | (1, 7) | 底行左起第 2 个 |
| 15 | (1, 0) | 顶行左起第 2 个 |
| **63** | (7, 0) | 第 0 块最后一颗 = 屏幕上部靠右 |
| **64** | (8, 7) | 第 1 块起点 = 底行左起第 9 个 |
| 65 | (8, 0) | 顶行左起第 9 个 |
| **127** | (15, 0) | 第 1 块右上 |
| **128** | (16, 7) | 第 2 块起点 |
| **191** | (23, 0) | 第 2 块右上 |
| **192** | (24, 7) | 第 3 块起点 |
| **255** | (31, 0) | 全串最后一颗 = **屏幕右上角** |

**最简验证：点亮串号 0，灯应该出现在屏幕左下角。** 如果它出现在左上角，`(7 - y)` 这一项写成了 `y`；如果出现在右上角，两项都反了。

## 3.4 单块内部的轴向（左旋 90° 的含义）

每块 8×8 模块，它的行方向不是横向，而是**被竖着放**了 —— 详见 README 里的示意图。结果就是：

- 屏幕的 **Y**（垂直方向）对应模块的**行内偏移**，且方向相反
- 屏幕的**块内 X** 对应模块的**行号**

这就是为什么公式里 `(7 - y)` 和 `(x % 8) * 8` 这两项位置"看起来反了"。

> 不要把 `TILE_ROTATE_LEFT_90` 理解成软件里旋转了 90° —— **它描述的是模块的物理安装朝向**。改动它等价于把每块模块转 90° 重新焊。

## 3.5 错误写法与对应症状（排错速查表）

| 错误写法 | 现象 |
|---|---|
| `index = y * 32 + x`（逐行） | 画面完全破碎，只能看到杂乱条纹 |
| `index = y * 32 + (y & 1 ? 31 - x : x)`（蛇形） | 偶数行正常，**奇数行左右镜像**，像被折过的纸 |
| `index = tile*64 + (x%8)*8 + y`（旋转方向反） | 画面**上下镜像**（顶部内容跑到底部） |
| `index = (x/8)*64 + y*8 + (7 - (x%8))`（行列互相错位） | 每块内部变成另一套装朝向，画面倾斜/扫帚状 |
| 忘了 `* 64` 的 tile base，或用了 `(3 - x/8)` | **四块的画面块位置互换**，但每块内部是对的 |
| 串的顺序接反（DIN 从右往左进入） | 整屏上下/块序错乱（注意这是**接线错**，不是公式错） |

**排错优先级：** 先单独点亮串号 0 和串号 255 确认轴向 → 再逐块看 tile 顺序 → 最后才是块内细节。

## 3.6 UDP 像素载荷的顺序

**约定：上位机按逻辑 XY 行序发送，不做任何硬件映射。**

```
payload[i]，i = 0 .. 255:
    x = i % 32      (0..31，行优先)
    y = i / 32      (0..7)
    payload[i] = R, payload[i+1] = G, payload[i+2] = B
    （每像素 3 字节，RGB，共 768 字节）
```

也就是标准的 **row-major、原点左上角、行优先**图像缓冲，跟你在上位机里画的 canvas 完全一致。

**好处：**
- 上位机不需要知道模块是怎么转的、是几块拼的、有没有蛇形——换硬件排布不用改上位机。
- 未来如果改排布（比如换成 2×2），只改固件一个函数。
- 测试时直接用一张 PNG 逐行取 RGB 就能当数据源。

**代价：** ESP8266 每帧要做 256 次坐标变换。这个代价可以认为是零 —— 因为 `x / 8` 和 `x % 8` 的除数是 2 的幂，编译器会优化成位移和按位与。

如果想彻底消除这点开销，启动时预计算一张 256 项的查表：

```cpp
static uint16_t kIndexLUT[256];
void buildIndexLUT() {
    for (uint16_t i = 0; i < 256; ++i) {
        uint8_t x = i % 32, y = i / 32;
        kIndexLUT[i] = xyToIndex(x, y);
    }
}
// 渲染：
// for (i = 0; i < 256; ++i)
//     strip.SetPixelColor(kIndexLUT[i], RgbColor(buf[3*i], buf[3*i+1], buf[3*i+2]));
```

## 3.7 性能提示

- **`strip.SetPixelColor()` 是按 raw index 寻址的**，而 UDP 载荷是按 XY 行序 → 每帧一定有一次重映射，别漏。
- 反过来千万别图省事：把 XY 载荷**直接 memcpy 到 DMA 缓冲**跳过重映射。这样出来的画面是错的，但又是"稳定地错"，很容易误判成"总线没问题、是对方发错了数据包"。
- 建议在固件启动阶段先用 **已知图案**（边框、对角条）验证一次映射，而不是直接跳到 UDP 接收。这正是**阶段 0 固件**的存在理由。
