# 06 · 彩虹时钟与兜底显示

> 适用状态：**CLOCK**（灯阵超时 5 s 且时间已同步）与 **WAITING**（超时且时间未同步）。

---

## 6.1 屏幕分区 —— HH:MM:SS

> **用户要求：24 小时制，含秒，格式 `00:00:00`。**

```
   x:  0 │ 1-4 │5│ 6-9 │10│11│ 12-15 │16│ 17-20 │21│22│ 23-26 │27│ 28-31
         │ H1  │ │ H2  │ :│  │  M1   │  │  M2   │ :│  │  S1   │  │  S2
  y=0..6 │         HH : MM : SS        │
  y=7    │ 底行秒进度 32px（0..59 秒） │
```

| 常量 | 值 | 说明 |
|---|---|---|
| `kClockWidth` | 32 | 整屏都是时钟区 |
| `kClockTop` | 0 | 字高 7，`(8-7)/2 = 0` |
| `kDigitW` | **4** | ★ 窄体字模宽度，不是 5 |
| `kDigitX[6]` | `{1, 6, 12, 17, 23, 28}` | 六个数字的起始 x |
| `kColonX[2]` | `{10, 21}` | 两个冒号列，两点位于 **y = 2 和 y = 4** |
| 字模尺寸 | **4 × 7** | MSB = 最左列（bit3） |

**为什么必须用 4 宽字模**：32 列要放 6 位数字 + 2 个冒号，5×7 字模需要 `6×5 + 3 + 2×2 = 37` 列，超 5 列。改用 4 宽后 `6×4 + 3 + 2×2 = 31` 列，加 1 列左边距正好 32。

第 7 行（y=7）留给底行秒进度，与字模不冲突。

## 6.2 4×7 窄体数字字模

```cpp
const uint8_t kDigitFont[10][7] = {
    {0b0110, 0b1001, 0b1001, 0b1001, 0b1001, 0b1001, 0b0110},  // 0  14 颗
    {0b0010, 0b0110, 0b0010, 0b0010, 0b0010, 0b0010, 0b0111},  // 1  10 颗
    {0b0110, 0b1001, 0b0001, 0b0010, 0b0100, 0b1000, 0b1111},  // 2  12 颗
    {0b0110, 0b1001, 0b0001, 0b0011, 0b0001, 0b1001, 0b0110},  // 3  12 颗
    {0b0001, 0b0011, 0b0101, 0b1001, 0b1111, 0b0001, 0b0001},  // 4  13 颗
    {0b1111, 0b1000, 0b1110, 0b0001, 0b0001, 0b1001, 0b0110},  // 5  14 颗
    {0b0110, 0b1000, 0b1110, 0b1001, 0b1001, 0b1001, 0b0110},  // 6  14 颗
    {0b1111, 0b0001, 0b0010, 0b0100, 0b1000, 0b1000, 0b1000},  // 7  10 颗
    {0b0110, 0b1001, 0b1001, 0b0110, 0b1001, 0b1001, 0b0110},  // 8  14 颗
    {0b0110, 0b1001, 0b1001, 0b0111, 0b0001, 0b0010, 0b1100},  // 9  13 颗
};

// 绘制：bit 3 (0x08) 是最左列
for (uint8_t row = 0; row < 7; ++row) {
    uint8_t bits = kDigitFont[digit][row];
    for (uint8_t col = 0; col < 4; ++col) {
        if (bits & (0x08 >> col)) setPixelXY(x0 + col, kClockTop + row, r, g, b);
    }
}
```

每位点亮 10~14 颗（平均 12.6）。六位最坏 **84 颗**（`00:00:00` 这种全是 0/8 的组合），加两个冒号 4 颗、底行 32 颗 —— 这是 [05](05-power-budget.md) 的预算依据。

## 6.3 冒号

```cpp
// 两个冒号，白色常亮
const uint8_t cv = vMax > 200 ? 200 : (vMax < 60 ? 60 : vMax);
for (uint8_t i = 0; i < 2; ++i) {
    setPixelXY(kColonX[i], 2, cv, cv, cv);
    setPixelXY(kColonX[i], 4, cv, cv, cv);
}
```

白色（不受彩虹色相影响）。**注意改成 HH:MM:SS 后冒号不再闪烁** —— 秒已经用数字显示了，再闪反而像时钟在重启。

## 6.4 底行秒进度（y=7，三种样式可切换）

时钟占满 32 列后原来的右侧 8×8 装饰区没有位置了，秒的"动感"由底行承担。短按板载 FLASH 键切换（见 `config.h` 的 `SecRowVariant`）：

| 样式 | 枚举 | 说明 |
|---|---|---|
| **秒进度条** | `SECROW_BAR`（默认） | 0..59 秒映射到 32 px，走过部分由暗到亮（0.35→0.80 × V），未走过留 5% 底 |
| 关闭 | `SECROW_OFF` | 底行全黑，最省电 |
| 刻度 | `SECROW_TICKS` | 每 5 秒一个刻度点，已过的 22%、当前区间 85%、未到 6% |

> 功耗上这条轨道很便宜（多数像素在中低明度），建议保留 —— 它让静止的时钟有了"活着"的感觉。

## 6.5 关于 emoji 区块（已取消）

原本规划在右侧 8 列放 emoji。改成 HH:MM:SS 后 32 列被数字占满，这块没有位置了。

顺带记录一下当初的结论：**8×8 只有 64 个像素，画不出手机那种表情形笔画**，只够做符号级像素画（心、笑脸、电池、WiFi 的程度）。真要丰富的表情得换更高密度的屏。

### 最坏-case 电流

用 `tools/clock_preview.py --scan` 扫全部 HH:MM:SS 组合，最坏的是 **00:00:58** —— 六个数字全是笔画最密的组合，且秒进度条几乎全满：

| V | 秒进度条 | 关闭 | 刻度 |
|---|---|---|---|
| 32 | 397 mA | 331 | 364 |
| 40 | 496 mA | 414 | 454 |
| **48（固件默认）** | **595 mA** | 497 | 545 |
| 64 | 794 mA | 662 | 727 |
| 72 | 893 mA ⚠ | 745 | 818 |

估算模型：`I(mA) = 0.0784 × Σ(R+G+B)`，且 HSV 饱和时必有一通道为 0，故 `Σ ≈ 1.5 × V`。

**结论：默认 V=56。** 它和参考工程实测观感的 V=50 接近，同时给 1000 mA 封顶留了足够余量。V=96 会触发封顶导致整体压暗、彩虹色相偏色，不推荐。

## 6.6 彩虹：横向渐变 + 整体滚动（用户已选）

```
屏上第 x 列的色相： hue(x) = (baseHue + x * 300° / 31) mod 360°
                          ≈ baseHue + 9.68° × x
baseHue 每 10 秒前进 360°  →  60 fps 下每帧 +0.6°
饱和度 S = 255（恒定，不要降 —— 见 05.3）
明度   V = 生效明度（建议起步 60~80，见 05.3）
```

32 列上铺开 300° 而不是整整 360°，目的是让左右两端有色差（同色不全域重合），看起来更像一条流动的光带而不是一个环。

### HSV → RGB（不要用参考工程的 `wheel()`）

参考工程的 `wheel()`：

```cpp
// 分段中间位置：r=128, g=126, b=0 —— 最亮通道只有 128
// → 色相过渡处明度掉到约 47%，彩虹看起来"一段亮一段暗"
```

正确做法用标准 HSV→RGB，保持各色相恒定最亮通道：

```cpp
// h: 0..255 色相轮；s, v: 0..255
void hsvToRgb(uint8_t h, uint8_t s, uint8_t v, uint8_t& r, uint8_t& g, uint8_t& b) {
    const uint8_t region     = h / 43;
    const uint8_t remainder  = (uint8_t)((h - region * 43) * 6);  // 0..255
    const uint16_t sp = (uint16_t)(((uint16_t)s * (uint16_t)remainder) >> 8);
    const uint16_t sq = (uint16_t)(((uint16_t)s * (uint16_t)(255 - remainder)) >> 8);
    const uint8_t  p  = (uint8_t)(((uint16_t)v * (uint16_t)(255 - s)) >> 8);
    const uint8_t  q  = (uint8_t)(((uint16_t)v * (uint16_t)(255 - sp))  >> 8);
    const uint8_t  t  = (uint8_t)(((uint16_t)v * (uint16_t)(255 - sq))  >> 8);
    switch (region) {
        case 0:  r = v; g = t; b = p; break;
        case 1:  r = q; g = v; b = p; break;
        case 2:  r = p; g = v; b = t; break;
        case 3:  r = p; g = q; b = v; break;
        case 4:  r = t; g = p; b = v; break;
        default: r = v; g = p; b = q; break;
    }
}
```

> **功耗提示**：改用 HSV 后色相不再"中段变暗"，平均 (R+G+B) 回到 1.5×255，电流比 `wheel()` 版本高。这正是 [05](05-power-budget.md) 的预算表按 1.5×255 计算的原因 —— 已经把这个成本算进去了。

## 6.7 NTP 时间同步

### 配置（照搬参考工程已验证的参数）

| 项 | 值 |
|---|---|
| 时区 | `"CST-8"` |
| NTP 服务器 | `ntp.aliyun.com` / `ntp.ntsc.ac.cn` / `pool.ntp.org` |
| WiFi 省电 | `WIFI_DISABLE_POWER_SAVE = true` |
| 有效性阈值 | `kValidUnixThreshold = 1700000000`（2023-11 之后） |

### ⚠️ 时区二次偏移的坑

**错误写法：**
```cpp
configTime(8 * 3600, 0, "ntp.aliyun.com");   // 传入偏移量
// 这样 time() 返回的已经是偏移后的值，若再套 localtime()/gmtime()
// 会在已偏的基础上再偏一次
```

**正确写法（推荐）：**
```cpp
configTzTime("CST-8", "ntp.aliyun.com", "ntp.ntsc.ac.cn", "pool.ntp.org");
// configTzTime 内部会 setenv("TZ", "CST-8", 1) + tzset()
// time() 返回 UTC epoch，localtime() 才做东八区转换 —— 语义明确，不会重复偏移
```

### 2 小时重同步

ESP8266 Arduino core 的 lwIP 默认 SNTP 重同步间隔约 **60 分钟**。用户要求改为 **2 小时**，两条路：

1. **调 lwIP**：`sntp_set_update_delay(7200000);`
   > ❌ **2026-09-18 实测：本环境不可用。** `framework-arduinoespressif8266 @ 3.1.2` 下，
   > `tools/sdk/lwip2/include/lwip/apps/sntp.h` 和 SDK 的 `tools/sdk/include/sntp.h`
   > **都没有这个声明**（后者只导出 `sntp_get/set_timezone` 那几个）。编译直接报
   > `not declared in this scope`。别再浪费时间找它。
2. **固件自己做**（✅ **已采用**）：每 2 小时重新调用一次 `configTzTime()` 强制刷新。
   不依赖任何 lwIP 内部符号，core 升级也不会失效。

> 结论：**只用方案 2。** 当初文档里"两者同时做"的建议已作废 —— 方案 1 在本环境下不存在。

### 判据

```cpp
bool isTimeValid() { return time(nullptr) > 1700000000; }
```

用于区分 CLOCK 与 WAITING。注意 NTP 失败时 `time()` 返回的是 1970 附近的小值，这个判断能干净地把两种情况分开。

## 6.8 WAITING 兜底

时间未同步时的显示：**"WAITING" 横向滚动**。

- 需要一套 5×7 的字母字模（参考工程里有 `kTextGlyphs`，含 8 行字形，可裁剪到 5×7 或直接用 8 行版本）。
- 滚动帧间隔参考既有实现：**80 ms/列**。
- 颜色建议用单色而不是彩虹：WAITING 是"异常态"，用暗橙/琥珀色更能传达"还没准备好"，同时省电。

> 不要用全白。全白在这块屏上意味着接近 15 A 的理论上限，即使是滚动文字，也要先过一遍 [05](05-power-budget.md) 的封顶。

## 6.9 状态切换时的观感处理

LIVE → CLOCK 的瞬间不要硬切（会看到画面突变）。建议做一个 200~300 ms 的淡入：

- CLOCK 时 **V 从 0 渐升到目标值**（约 250 ms）。
- CLOCK → LIVE 则相反：不是渐隐，而是**等下一帧 pixels 包到来时直接覆盖**（已有 UDP 帧说明上位机回来了，拖一帧反而别扭）。
